# 写给人看的文档

## 为什么需要这个 skill

你在维护项目时，上下文里装着整个项目，处在"全都知道"的状态。所以你很难察觉哪些词对外人是一堵墙、哪条信息对新人最要紧。你写出来的文档通常准确、完整，但读者要自己挑重点、自己推结论。

这个 skill 的作用是：每次写文档时，强制切换到"第一次来的人"的视角。

## 写之前

1. **确认读者。** 默认读者是：第一次来、不了解项目内部、想尽快判断"这东西跟我有没有关系、怎么开始"的人。
2. **读产品意图。** 如果项目里有 `PRODUCT.md`（或类似的意图文档），先读它。它说明了项目给谁用、主路径是什么、刻意不做什么。取舍以它为准，不要自己发明产品方向。如果没有，不要替用户编，可以在最后建议补一份（模板见文末）。

## 开头：先回答三个问题

README 的前几行必须让读者知道：

- **这是什么**：一句话，用读者懂的词。不要用项目内部的模块名来解释项目。
- **给谁用 / 解决什么问题**
- **怎么开始**：最短路径，一条命令或一个链接。

能用三四句话说完就不要写成一个章节。

## 筛选：留什么、删什么、挪到哪

对每条信息问一句："第一次来的人需要现在知道这个吗？"

- **留在前面**：是什么、怎么开始、最常见的用法、会让人踩坑的变化。
- **挪到后面或别的文件**：版本号表格、提交 hash、内部架构、完整配置项、发布记录。
- **删掉**：读者根本不会产生的误解。"本仓库不是 X，也不是 Y" 这类否定句，通常是在纠正你自己上下文里的误会，读者不需要。只有当读者**真的很可能**这么误解时才保留，并且改成正面表述（说它是什么，而不是不是什么）。

## 消化：把事实转成结论

重要信息不能只给原始事实，要替读者把结论推出来，用他能直接行动的话说。

不好：
> 新 Skill 要求 Runtime >= 0.5.9 且实际能力匹配，当前公开下载为 v0.4.11。

好：
> 新功能需要 Runtime 0.5.9 以上，但目前公开版只到 0.4.11，**所以现在安装后暂时用不了新功能**。等 Runtime 发布后再升级即可。

原则：
- 先说结论，再给依据。
- 有变化时说清三件事：改了什么、为什么改、不接受这个变化怎么办。
- 自造术语要么换成普通说法，要么第一次出现时用一句话解释。

## 分层：别把三种文档搅在一起

| 文件 | 读者 | 放什么 |
|---|---|---|
| `README.md` | 第一次来的人 | 是什么、怎么开始、重要提醒、去哪看更多 |
| `CHANGELOG.md` / Release | 已经在用的人、维护者 | 版本、提交、兼容性细节 |
| `AGENTS.md` / 知识库 | AI 和维护者 | 约定、边界、内部结构 |

如果发现 README 里混着另外两类内容，挪走它们，README 里留一句链接。

## 更新已有文档时

- 不要只在顶部追加"本次发布"。README 顶部永远留给新人。
- 本次改动如果影响用户，把它**消化**成一条提醒放进 README，细节进 CHANGELOG。
- 顺手检查：旧内容是否已过时？过时就删，不要叠加。

## 写完后：新人检查

假装你完全没有这个项目的上下文，只读 README 的前一屏，回答：

1. 这东西是干嘛的？
2. 我该怎么开始？
3. 有没有什么我必须知道的坑？

任何一个答不出来，或者需要读两遍才懂，就回去改。如果条件允许，建议用户开一个**没有项目上下文的新对话**，只贴 README 让它回答这三个问题，这比自查更可靠。

## 附：产品意图模板

建议放在仓库根目录 `PRODUCT.md`，由人来写，半页以内：

```markdown
# 产品意图

## 给谁用
一句话描述目标用户。

## 主路径
用户最常做的那件事，从打开到完成的几步。

## 刻意不做
列出明确不做的方向，以及一句原因。

## 文档原则（可选）
比如：README 只讲上手，细节去官方文档。
```
